# 은마아파트입구 일대 소통정보 수집

서울시 TOPIS 소통정보에서 은마아파트입구 사거리를 지나는 4개 경로의 구간 평균속도를
정기적으로 수집해 `data/traffic_log.csv`에 누적 저장한다.

## 수집 경로

| 경로 | 도로 | 방향 | 구간 |
|---|---|---|---|
| 1 | 도곡로 | 상행 | 한티역 → 은마아파트입구 → 대치동우성아파트 |
| 2 | 도곡로 | 하행 | 대치동우성아파트 → 은마아파트입구 → 한티역 |
| 3 | 삼성로 | 상행 | 대치사거리 → 은마아파트입구 → 대치역 |
| 4 | 삼성로 | 하행 | 대치역 → 은마아파트입구 → 대치사거리 |

경로당 2개 구간씩, 1회 실행에 8행이 쌓인다.

## 실행 주기

**실제 5분 간격 수집은 외부 크론 서비스(cron-job.org)가 담당한다.** KST 16:00~23:00
사이 5분마다 GitHub REST API(`workflow_dispatch`)를 직접 호출해 워크플로를 실행시킨다.

GitHub 자체의 `schedule` 트리거는 안전망 용도로만 남겨뒀다 — 매시 정각에 한 번씩만
돈다. GitHub의 예약 실행은 5분처럼 짧은 주기에서 수십 분씩 지연되거나 실행이
누락되는 경우가 잦아(2026-08-01~04 실행 이력에서 확인), 그 자체로는 5분 간격을
보장할 수 없다.

기록된 `timestamp_kst`는 트리거 예정 시각이 아니라 실제 API 호출 시각이다.

수동 실행은 Actions 탭의 `Run workflow` 버튼으로 한다.

카카오톡 알림은 데이터 수집과 별개로 **30분 간격**으로만 발송된다 (Claude 예약 작업).

## CSV 형식

`data/traffic_log.csv`

| 컬럼 | 설명 |
|---|---|
| timestamp_kst | API 호출 시각 (KST, 분 단위) |
| axisNm | 도로명 — 도곡로 / 삼성로 |
| axisDirDivCd | 방향코드 — 1(상행) / 2(하행) |
| axisDirDivNm | 방향명 |
| stNodeNm / edNodeNm | 구간 시작·종료 지점 |
| speed | 구간 평균속도 (km/h) |
| trfClsNm | 소통상태 — 원활 / 서행 / 정체 |

기존 로그는 삼성로만 수집해 `axisNm` 컬럼이 없었다. 도곡로가 추가되면서 이 컬럼이
생겼고, 이전 행들은 모두 삼성로이므로 그 값으로 채워 넣었다.

## 데이터 출처와 갱신 주기

TOPIS `selectRoadDetailList.do` 엔드포인트를 직접 호출한다. 일반도로 소통정보는
서울시 카드택시 GPS를 기반으로 **5분 단위** 구간속도로 산출된다. 수집 주기를 원본
갱신 주기와 같은 5분으로 맞췄으므로, 이론상 매 갱신 시점을 놓치지 않고 기록한다.

python collect_topis.py
